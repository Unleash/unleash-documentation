<Markdown src="/snippets/sdks/backend-intro.mdx" language="Python" />

The SDK includes two clients: `UnleashClient` for synchronous applications and `AsyncUnleashClient`, an asyncio-native client for applications built on frameworks such as FastAPI, Starlette, or aiohttp. Both expose the same API for evaluating flags; they differ only in how you initialize and stop them.

## Requirements

- Python 3.8 or later

## Installation

Install the SDK from PyPI:

```bash
pip install UnleashClient
```

## Initialization

<Markdown src="/snippets/sdks/backend-singleton-warning.mdx" />

<Markdown src="/snippets/sdks/backend-connection.mdx" />

Flag checks are regular synchronous methods on both clients, because evaluation happens locally against the SDK's cached configuration and performs no I/O. Only the async client's lifecycle methods are coroutines. The async client communicates with Unleash using [aiohttp](https://docs.aiohttp.org/), which is installed as a dependency of the SDK.

<Tabs>
<Tab title="Sync">

```python
from UnleashClient import UnleashClient

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
)

client.initialize_client()
```

You can also use the client as a context manager, which initializes the client on entry and shuts it down on exit:

```python
with UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
) as client:
    client.is_enabled("my-flag")
```

</Tab>
<Tab title="Async">

```python
from UnleashClient import AsyncUnleashClient

client = AsyncUnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
)

await client.initialize_client()
```

You can also use the client as an async context manager, which initializes the client on entry and shuts it down on exit:

```python
async with AsyncUnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
) as client:
    client.is_enabled("my-flag")
```

</Tab>
</Tabs>

### Check if the SDK is ready

Until the SDK has synchronized with Unleash, all flags evaluate to `false` and variants resolve to the [disabled variant](/concepts/feature-flag-variants#the-disabled-variant), unless you have a [bootstrapped configuration](#bootstrap) or use a [fallback function](#fallback-function).

Use the `is_initialized` property to check whether the SDK has loaded flag configuration, or subscribe to the `READY` [event](#events) to get notified when the SDK first loads flags from the Unleash server or the local cache.

```python
if client.is_initialized:
    enabled = client.is_enabled("my-flag")
```

### Streaming

<span data-badge-type="availability" title="Beta" class="fern-docs-badge large blue subtle rounded-full">Beta</span>

By default, the SDK polls Unleash at a fixed interval. Streaming mode receives flag updates in real time using server-sent events, reducing the delay between a change in Unleash and the SDK applying the updated configuration.

Streaming requires [Unleash Enterprise Edge](/unleash-edge). To enable it, point `url` at your Enterprise Edge instance, provide a valid backend token, and set `experimental_mode` to streaming:

```python
client = UnleashClient(
    url="https://<your-edge-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    experimental_mode={"type": "streaming"},
)

client.initialize_client()
```

## Check flags

Use `is_enabled` to evaluate a flag. Evaluation happens locally against the SDK's cached configuration.

```python
if client.is_enabled("my-flag"):
    # new behavior
    ...
```

### Check variants

Use `get_variant` to evaluate a flag with [variants](/concepts/feature-flag-variants). The method returns a dictionary:

```python
variant = client.get_variant("my-flag")

# {
#     "name": "variant1",
#     "payload": {"type": "string", "value": "val1"},
#     "enabled": True,
#     "feature_enabled": True,
# }
```

The SDK can return two forms of the disabled variant. In both cases, `name` is `disabled` and `enabled` is `False`:

<Tabs>
<Tab title="Flag disabled or not found">

```python
{
    "name": "disabled",
    "enabled": False,
    "feature_enabled": False,
}
```

</Tab>
<Tab title="Flag enabled, no variant resolved">

The flag is enabled but no variant applies, for example when the flag has no variants configured:

```python
{
    "name": "disabled",
    "enabled": False,
    "feature_enabled": True,
}
```

</Tab>
</Tabs>

Use `feature_enabled` when you need the flag's state alongside the variant result, without a separate `is_enabled` call.

### Fallback function

You can specify a fallback function for cases where the client doesn't recognize the flag by using the `fallback_function` keyword argument:

```python
def custom_fallback(feature_name: str, context: dict) -> bool:
    return True

client.is_enabled("my-flag", fallback_function=custom_fallback)
```

The fallback function must accept the feature name and context as positional arguments, in that order.

The client evaluates the fallback function if the feature flag is not found or if an exception occurs during evaluation. If the fallback function itself raises an exception, `is_enabled` returns `False` and logs a warning.

## Unleash context

<Markdown src="/snippets/sdks/unleash-context-intro.mdx" />

Both `is_enabled` and `get_variant` accept a context dictionary as the second parameter:

```python
app_context = {
    "userId": "user-123",
    "sessionId": "session-abc",
    "properties": {
        "custom-property": "some-value"
    }
}

client.is_enabled("my-flag", app_context)
client.get_variant("my-flag", app_context)
```

The SDK enriches the context automatically before evaluation:

- `appName` and `environment` are set from the client configuration.
- `currentTime` is set to the current UTC time when you don't provide it, so date-based constraints work without extra setup.
- Any top-level key that isn't a standard context field is moved into `properties`. Passing `{"custom-property": "some-value"}` at the top level is equivalent to nesting it under `properties`.

Context values can be any type that has a `__str__` implementation. Explicitly supported types are:

- Numerics
- Strings
- Dates
- UUIDs

<Note>
Gradual rollout strategies require you to pass either a `userId` or a `sessionId` for [stickiness](/concepts/stickiness) to work correctly.
</Note>

## Stop the client

Call `destroy()` to shut down the SDK and flush any pending metrics to Unleash. If you use the client as a context manager, this happens automatically on exit.

<Tabs>
<Tab title="Sync">

```python
client.destroy()
```

</Tab>
<Tab title="Async">

```python
await client.destroy()
```

</Tab>
</Tabs>

A destroyed client cannot be reinitialized. Create a new instance if you need to reconnect.

## Custom strategies

The SDK supports all [built-in activation strategies](/concepts/activation-strategies). You can also define [custom activation strategies](/concepts/custom-activation-strategies) if the built-in ones don't cover your needs.

A custom strategy is a class that implements an `apply` method:

```python
class ActiveForEmailStrategy:
    def apply(self, parameters: dict, context: dict = None) -> bool:
        # Decide if the feature is active for this context
        return context.get("email") in parameters
```

Once you've defined your strategy, register it when you initialize the client. The key must exactly match the strategy name in Unleash:

```python
# Requires a custom strategy defined in Unleash called 'EmailStrategy'
my_custom_strategies = {
    "EmailStrategy": ActiveForEmailStrategy()
}

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    custom_strategies=my_custom_strategies,
)
```

## Events

To subscribe to SDK events, provide an `event_callback` function when you initialize the client. The callback receives a single event object.

| Event type | Description |
|------------|-------------|
| `READY` | The SDK loaded feature flags from the Unleash server or the local cache. Emitted once. |
| `FETCHED` | A new version of the feature flags was fetched from the server. The event includes a `features` property with all flags returned by that fetch. |
| `FEATURE_FLAG` | A flag with [impression data](/concepts/impression-data) enabled was evaluated with `is_enabled`. |
| `VARIANT` | A flag with impression data enabled was evaluated with `get_variant`. |

The SDK invokes your callback on a dedicated background thread. Flag evaluation does not wait for the callback, so a slow callback cannot block your application. Two consequences of this design:

- The callback cannot read thread-local state from the calling thread, such as Flask's `g` object, the current Django request, or `contextvars`.
- If the callback cannot keep up, the SDK drops events and logs a warning instead of blocking.

Set `event_callback` when you construct the client; reassigning it afterwards has no effect.

<Note>
The SDK does not include a built-in event bus. The example below uses [Blinker](https://pypi.org/project/blinker/) to send signals.
</Note>

```python
from blinker import signal
from UnleashClient import UnleashClient
from UnleashClient.events import UnleashEvent, UnleashEventType

send_data = signal('send-data')

@send_data.connect
def receive_data(sender, **kw):
    if kw["data"].event_type == UnleashEventType.READY:
        print("SDK is ready: flags loaded from Unleash or local cache")
    elif kw["data"].event_type == UnleashEventType.FETCHED:
        print("Fetched new feature flags:", kw["data"].features)

def example_callback(event: UnleashEvent):
    send_data.send('anonymous', data=event)

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    event_callback=example_callback,
)
client.initialize_client()
client.is_enabled("my-flag")
```

### Impression data

<Markdown src="/snippets/sdks/impression-data-intro.mdx" />

Impression events arrive through the same `event_callback` with the event types `FEATURE_FLAG` and `VARIANT`. Each event includes the `feature_name`, the `enabled` result, and, for variant checks, the `variant` name:

```python
from UnleashClient.events import UnleashEvent, UnleashEventType

def example_callback(event: UnleashEvent):
    if event.event_type == UnleashEventType.FEATURE_FLAG:
        print(f"{event.feature_name} evaluated to {event.enabled}")
    elif event.event_type == UnleashEventType.VARIANT:
        print(f"{event.feature_name} resolved to variant {event.variant}")
```

## Impact metrics

<Markdown src="/snippets/sdks/impact-metrics.mdx" />

The SDK automatically attaches `appName` and `environment` labels to all impact metrics.

Define and record metrics through the client's `impact_metrics` property:

```python
from UnleashClient import UnleashClient

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
)
client.initialize_client()

client.impact_metrics.define_counter("request_count", "Total number of HTTP requests")
client.impact_metrics.increment_counter("request_count")

client.impact_metrics.define_gauge("active_users", "Current number of active users")
client.impact_metrics.update_gauge("active_users", 42)

client.impact_metrics.define_histogram(
    "request_time_ms",
    "Request processing time in milliseconds",
    buckets=[50, 100, 200, 500, 1000],
)
client.impact_metrics.observe_histogram("request_time_ms", 125)
```

### Metric types

<Tabs>
<Tab title="Counter">

Use counters for cumulative values that only increase, such as the total number of requests or errors.

```python
client.impact_metrics.define_counter("request_count", "Total number of HTTP requests")
client.impact_metrics.increment_counter("request_count")
```

</Tab>
<Tab title="Gauge">

Use gauges for values that can go up or down, such as current memory usage or active user count.

```python
client.impact_metrics.define_gauge("active_users", "Current number of active users")
client.impact_metrics.update_gauge("active_users", 42)
```

</Tab>
<Tab title="Histogram">

Histograms measure distributions such as latency or payload size.

```python
client.impact_metrics.define_histogram(
    "request_time_ms",
    "Request processing time in milliseconds",
    buckets=[50, 100, 200, 500, 1000],
)
client.impact_metrics.observe_histogram("request_time_ms", 125)
```

</Tab>
</Tabs>

Impact metrics are batched and sent on the same interval as standard SDK metrics, controlled by `metrics_interval`.

## Bootstrap

By default, the SDK fetches your feature flags from the Unleash API at startup. To make your application more resilient, for example during network outages, you can bootstrap the client with a local or remote flag configuration:

1. Create a `FileCache`, or your own `BaseCache` implementation.
2. Pre-seed it with feature flags using `bootstrap_from_dict`, `bootstrap_from_file`, or `bootstrap_from_url`.
3. Pass the cache to the `UnleashClient` constructor.

A bootstrapped client can evaluate flags immediately, before its first fetch from Unleash completes.

<Tabs>
<Tab title="Dictionary">
```python
from UnleashClient.cache import FileCache
from UnleashClient import UnleashClient

cache = FileCache("my-cache")
cache.bootstrap_from_dict({
    "version": 2,
    "features": [
        {
            "name": "my-flag",
            "enabled": True,
            "strategies": [{"name": "default"}],
        }
    ]
})

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    cache=cache,
)
```
</Tab>
<Tab title="File">
```python
from pathlib import Path
from UnleashClient.cache import FileCache
from UnleashClient import UnleashClient

cache = FileCache("my-cache")
cache.bootstrap_from_file(Path("/path/to/your_bootstrap.json"))

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    cache=cache,
)
```
</Tab>
<Tab title="URL">
```python
from UnleashClient.cache import FileCache
from UnleashClient import UnleashClient

cache = FileCache("my-cache")
cache.bootstrap_from_url(
    "https://your-server/bootstrap.json",
    headers={"Authorization": "<token>"},
)

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    cache=cache,
)
```

The `headers` argument is optional; use it when the bootstrap URL requires authentication. You can also set `request_timeout`, in seconds, for the bootstrap request.
</Tab>
</Tabs>

## Local caching and offline behavior

The SDK persists the latest flag configuration to an on-disk cache between restarts, using [fcache](https://pypi.org/project/fcache/). Set `cache_directory` to control where the cache is stored.

On startup, the SDK loads cached state first, then fetches fresh configuration from Unleash. If Unleash is temporarily unreachable, the SDK continues serving cached or bootstrapped values and keeps polling on `refresh_interval`.

### Custom cache

If you need a different storage backend, for example Redis, memory-only, or a custom database, provide your own cache implementation that extends `BaseCache`.

Below is an example custom cache using fcache under the hood:

```python
from typing import Optional, Any
from UnleashClient.cache import BaseCache
from fcache.cache import FileCache as _FileCache

class CustomCache(BaseCache):
    # This is specific to FileCache. Depending on the cache you're using, this may look different.
    def __init__(self, name: str, directory: Optional[str] = None):
        self._cache = _FileCache(name, app_cache_dir=directory)

    def set(self, key: str, value: Any):
        self._cache[key] = value
        self._cache.sync()

    def mset(self, data: dict):
        self._cache.update(data)
        self._cache.sync()

    def get(self, key: str, default: Optional[Any] = None):
        return self._cache.get(key, default)

    def exists(self, key: str):
        return key in self._cache

    def destroy(self):
        return self._cache.delete()
```

Pass your cache instance to the client with the `cache` argument:

```python
client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
    cache=CustomCache("my-cache"),
)
```

## Framework integration

The SDK runs background jobs to keep feature flags in sync with the Unleash server. Some runtime environments, like WSGI servers and Celery workers, need extra setup to make sure the SDK works correctly.

### WSGI

When using WSGI servers, for example with Flask or Django apps, be aware that:

- Many WSGI setups disable threading by default. The SDK needs threads to poll for updates in the background, so set `enable-threads` in your WSGI config.
- When running under uWSGI with multiple processes using the `--processes` option, you may need to enable the `lazy-apps` option. This ensures each process gets a fresh SDK instance.

See [The Art of Graceful Reloading](https://uwsgi-docs.readthedocs.io/en/latest/articles/TheArtOfGracefulReloading.html#preforking-vs-lazy-apps-vs-lazy) for more details.

### Celery

When using the SDK in Celery tasks, initialize it inside the `worker_process_init` event. Otherwise, the worker may run but won't poll for feature flag updates.

```python
from UnleashClient import UnleashClient
from celery.signals import worker_process_init

client = UnleashClient(
    url="https://<your-unleash-instance>/api",
    app_name="my-python-app",
    custom_headers={"Authorization": "<your-backend-token>"},
)

@worker_process_init.connect
def configure_workers(sender=None, conf=None, **kwargs):
    client.initialize_client()
```

### Multi-process setups

In multi-process setups where one process keeps the on-disk cache fresh, other processes can call `initialize_client(fetch_toggles=False)`. The client then reads flag configuration from the cache instead of polling the Unleash API.

## Unit testing

To test code that depends on feature flags without a running Unleash instance, bootstrap a cache with the flag state you want and turn off all network activity:

```python
from UnleashClient import UnleashClient
from UnleashClient.cache import FileCache

def make_test_client(cache_dir: str) -> UnleashClient:
    cache = FileCache("test-cache", directory=cache_dir)
    cache.bootstrap_from_dict({
        "version": 2,
        "features": [
            {
                "name": "my-flag",
                "enabled": True,
                "strategies": [{"name": "default"}],
            }
        ]
    })

    client = UnleashClient(
        url="http://localhost:4242/api",
        app_name="test-app",
        disable_metrics=True,
        disable_registration=True,
        cache=cache,
    )
    client.initialize_client(fetch_toggles=False)
    return client

def test_my_feature(tmp_path):
    client = make_test_client(str(tmp_path))
    assert client.is_enabled("my-flag")
    client.destroy()
```

With `fetch_toggles=False`, the client loads flags from the cache only, so tests are deterministic and make no network requests.

## Troubleshooting

<AccordionGroup>
<Accordion title="All flags evaluate to false">

If `is_enabled` always returns `False`:

- Confirm the flag exists and is enabled in the target environment.
- Verify `url` points to your Unleash API base URL, for example `https://<your-unleash-instance>/api`.
- Verify `custom_headers` includes a valid backend API token in `Authorization`.
- Verify the SDK completed its initial sync: `is_initialized` is `True` or the `READY` event fired.
- Verify your [Unleash context](/concepts/unleash-context) fields match your rollout strategy and constraints.

</Accordion>
<Accordion title="Flags never update in uWSGI or Celery workers">

If the SDK initializes but flag changes never arrive:

- Under uWSGI, enable the `enable-threads` option; the SDK needs threads to poll in the background. With multiple processes, also consider `lazy-apps`.
- In Celery workers, initialize the client inside the `worker_process_init` signal.

See [Framework integration](#framework-integration) for details.

</Accordion>
</AccordionGroup>

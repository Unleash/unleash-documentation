[OpenFeature](https://openfeature.dev/) is an open standard and Cloud Native Computing Foundation (CNCF) project that provides a vendor-neutral API for feature flag evaluation. Your application code calls the OpenFeature SDK, and a [provider](https://openfeature.dev/docs/reference/concepts/provider) connects that SDK to a feature flag management system.

Unleash providers connect the OpenFeature SDK to Unleash. Each provider wraps an Unleash SDK, so Unleash still manages your flags, evaluates them, and collects usage metrics. Your application code depends only on the OpenFeature API.

## How it works

- Your application evaluates a flag through an OpenFeature client, for example `getBooleanValue("my-feature", false, context)`.
- The Unleash provider translates the OpenFeature [evaluation context](https://openfeature.dev/docs/reference/concepts/evaluation-context) into an [Unleash context](/concepts/unleash-context).
- The underlying Unleash SDK evaluates the flag, using the same caching, polling, and metrics behavior as when you use the SDK directly.
- The provider returns the result to OpenFeature as a typed value, together with evaluation details such as the variant name.

Backend providers, such as [Node.js](/sdks/openfeature/node) and [Python](/sdks/openfeature/python), wrap backend SDKs that evaluate flags locally and accept a context with every evaluation.
Frontend providers, such as [Swift](/sdks/openfeature/swift) and [Android](/sdks/openfeature/android), wrap frontend SDKs that fetch flags evaluated for one context at a time.
With a frontend provider, you set the context on the OpenFeature API, and changing it triggers a refetch from Unleash.

## When to use OpenFeature

OpenFeature is a good fit when:

-   Your organization standardizes on one feature flag API. Platform teams can give every service the same evaluation interface across languages and frameworks, and keep the choice of flag management system behind the provider.
-   You're migrating from another feature flag system. If your code already uses OpenFeature, you can switch to Unleash by swapping the provider, without changing evaluation call sites. See [Migrate from LaunchDarkly](/guides/feature-flag-migration-best-practices#migrate-from-launchdarkly) for a step-by-step migration that includes this approach.
-   You want to use OpenFeature hooks and ecosystem tooling. [Hooks](https://openfeature.dev/docs/reference/concepts/hooks) run custom logic before and after every flag evaluation, for use cases such as logging, telemetry, and validation. You register hooks on the OpenFeature API or client, so they work with the Unleash providers. Browse the [OpenFeature ecosystem](https://openfeature.dev/ecosystem) for available hooks.

If you don't need a vendor-neutral API, use the [Unleash SDK](/sdks) for your language. The Unleash SDKs support capabilities that the OpenFeature API doesn't model, as described in [OpenFeature providers compared with Unleash SDKs](#openfeature-providers-compared-with-unleash-sdks).

## Get started

Install the provider for your language, register it with OpenFeature, and evaluate a flag. Backend providers need a [backend token](/concepts/api-tokens-and-client-keys#backend-tokens), and frontend providers need a [frontend token](/concepts/api-tokens-and-client-keys#frontend-tokens).

use open_feature::{EvaluationContext, OpenFeature};
use unleash_api_client::ClientBuilder;
use unleash_openfeature_rust_provider::UnleashFlagProvider;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let provider = UnleashFlagProvider::new(
        ClientBuilder::default(),
        "<YOUR_UNLEASH_URL>/api",
        "my-rust-app",
        "my-rust-app-instance",
        Some("<YOUR_API_TOKEN>".to_string()),
    )?;
    provider.initialize_client().await?;

    api.set_provider(provider).await;

    let client = api.create_client();
    let context = EvaluationContext::default().with_targeting_key("user-123");

    let enabled = client
        .get_bool_value("my-feature", Some(&context), None)
        .await
        .unwrap_or(false);

    Ok(())
}

## How Unleash concepts map to OpenFeature

### Flag evaluation

OpenFeature defines typed evaluation methods. The Unleash providers resolve them as follows:

| OpenFeature method | Resolves from | Accepted payload types |
| --- | --- | --- |
| Boolean | The flag's enabled state | Not applicable |
| String | The payload of the flag's [variant](/concepts/feature-flag-variants) | `string`, `csv` |
| Number, integer, float, or double | The payload of the flag's variant | `number` |
| Object | The payload of the flag's variant | `json` |

Boolean evaluations return the flag's enabled state, so a disabled flag returns `false`. For non-Boolean evaluations, a disabled flag or a missing or mismatched variant payload returns the default value you pass to the evaluation method. When a variant is assigned, detail methods such as `getStringDetails` report its name. Unleash SDKs don't report why a flag evaluated the way it did, so most providers return the `UNKNOWN` evaluation reason.

### Context mapping

The Unleash providers follow the same rules to map the OpenFeature evaluation context to the [Unleash context](/concepts/unleash-context):

-   The targeting key maps to `userId` and takes precedence over a `userId` attribute.
-   Attributes named after top-level Unleash context fields, such as `sessionId` and `remoteAddress`, map to those fields.
-   All other scalar attributes become Unleash context [properties](/concepts/unleash-context#the-properties-field), which you can use in [strategy constraints](/concepts/activation-strategies#constraints). The providers discard nested values, such as lists and objects.

Each provider page lists the exact fields it maps.

<Warning>
Community providers can map the context differently. For example, some community providers don't map the targeting key to `userId`, or expect differently cased attribute names. Check the context mapping in the provider's documentation, or set `userId` explicitly, to make sure strategies that depend on `userId` behave as expected.
</Warning>

## OpenFeature providers compared with Unleash SDKs

OpenFeature models the capabilities that feature flag systems have in common. Unleash-specific capabilities that fall outside that common API aren't available through the providers. The following table compares the Unleash providers with the Unleash SDKs they wrap.

| Capability | Unleash SDKs | OpenFeature providers |
| --- | --- | --- |
| Flag evaluation with [activation strategies](/concepts/activation-strategies) and constraints | ✅ | ✅ |
| [Variants](/concepts/feature-flag-variants) and payloads | ✅ Variant name and payload | ✅ Payload as a typed value, variant name in evaluation details |
| [Unleash context](/concepts/unleash-context) and custom properties | ✅ | ✅ Mapped from the evaluation context |
| Usage metrics | ✅ | ✅ Reported by the wrapped SDK |
| [Impression data](/concepts/impression-data) | ✅ | ❌ |
| [Impact metrics](/concepts/impact-metrics) and [safeguards](/concepts/impact-metrics#configure-safeguards) | ✅ | ❌ |
| Fallback function for unknown flags | ✅ Backend SDKs | ❌ |
| Direct access to the Unleash client | ✅ | ❌ |
| [Bootstrap](/sdks#bootstrap) | ✅ | Varies by provider |
| Client events, such as ready and configuration changed | ✅ Unleash SDK events | Varies by provider |

In exchange, OpenFeature adds capabilities that sit above any single provider, such as [hooks](https://openfeature.dev/docs/reference/concepts/hooks), named clients, and a consistent evaluation API across vendors. The Unleash providers don't implement the OpenFeature [tracking](https://openfeature.dev/docs/reference/concepts/tracking) API.

To use all Unleash capabilities, including impression data, impact metrics, and safeguards, use the [Unleash SDK](/sdks) for your language directly.

This guide helps you upgrade **Enterprise Edge self-hosted** from version 17 and newer to the latest release.

The recommended approach is to upgrade in **stages by major version**:

`v17 -> v18 -> latest v19 -> latest v20`

This reduces risk, makes troubleshooting easier, and gives you a clear rollback point after each major transition.

## Who this guide is for

Use this guide if you:

- Run Enterprise Edge in your own infrastructure.
- Plan to move from `v17.x`, `v18.x`, or `v19.x` to a newer major version.
- Need a repeatable runbook for UAT and production rollouts.

If you are using hosted Enterprise Edge, version rollouts are managed for you.

## Before you upgrade

Complete this checklist before changing versions:

1. Record current runtime details:
   - Edge image tag and chart version.
   - Current environment variables and startup arguments.
   - Persistence configuration (`REDIS_URL`, `S3_BUCKET_NAME`, `BACKUP_FOLDER`) if any.
2. Inventory tokens in use:
   - Startup tokens configured in `TOKENS`.
   - Which environments and projects each token covers.
   - Which client applications and SDKs depend on each token.
3. Confirm rollback readiness:
   - Previous image/chart version available.
   - Persistence snapshot/backup available.
   - Clear owner and window for rollback if validation fails.

## Recommended upgrade path

### Step 1: Upgrade v17 -> v18

Key migration point:

- Service-account-driven token creation support was removed in v18.

What to do:

- Start Edge with explicit, valid startup tokens in `TOKENS`.
- Ensure startup tokens cover the environments/projects your clients require.
- Do not rely on Edge creating missing client tokens at runtime.

### Step 2: Upgrade v18 -> latest v19

Key migration points in v19:

- Token handling and token-related behavior were tightened across v19.
- `v19.10.0` introduced pretrusted token support for specific migration scenarios.

What to do:

- Keep `TOKENS` aligned to real usage scope.
- If you need compatibility with legacy-style frontend token secrets during migration, evaluate `PRETRUSTED_TOKENS`.
- Validate that all expected SDK requests are covered by startup scope.

### Step 3: Upgrade latest v19 -> latest v20

Key migration points in v20:

- v20 is a major release and should be treated as a full regression checkpoint.
- Startup token scope remains central to successful feature delivery.

What to do:

- Keep explicit `TOKENS` configuration; verify coverage before rollout.
- Validate readiness and feature responses in UAT before production rollout.
- Apply the same validation checklist per environment.

## Upgrade runbook (UAT then production)

1. Deploy target version in UAT with the intended production configuration.
2. Validate startup and readiness:
   - `GET /internal-backstage/health` returns `200`.
   - `GET /internal-backstage/ready` returns `READY`.
3. Validate token and feature behavior:
   - Frontend API calls return expected toggles.
   - Client API calls return expected toggles.
   - No unexpected unauthorized/forbidden spikes.
4. Validate business-path behavior in at least one real application flow.
5. Roll out to production gradually (canary or phased).
6. Repeat health/readiness and feature validation checks in production.

## Troubleshooting: 19.7.0 -> 20.1.10 token failures

This section covers a common upgrade pattern where teams observe authorization failures after moving from `v19.7.0` to `v20.1.10`.

### Symptom pattern

- Applications that previously fetched flags start returning unauthorized responses.
- Failures may appear intermittent across clients or environments.
- Teams often discover mismatches between startup token scope and real client usage.

### Is token validation different in v20.1.10 vs v19.7.0?

In practical terms, upgrades can expose token-configuration gaps that were previously masked by older behavior or stale persisted state.

Action:

- Re-verify startup `TOKENS` and ensure they explicitly cover all required environments/projects.

### Do existing tokens need reconfiguration after upgrade?

Often, yes. Not because token format changed, but because startup scope must match real traffic.

Action:

- Rebuild the token inventory and map each token to actual client usage.
- Replace ambiguous or incomplete startup token sets with explicit coverage.

### Could stale persistence cause confusing behavior?

Yes. Persisted token/feature state can carry forward assumptions from previous versions.

Action:

- If behavior is inconsistent after upgrade, purge stale Edge persistence and let Edge rehydrate from upstream.
- Use caution and do this in a controlled window.

### Client token vs machine-to-machine/service-account token

Use valid **client/backend API tokens** for Edge startup token scope.

Action:

- Do not assume service-account-style credentials are interchangeable with client tokens for runtime feature delivery.
- Align token type and scope with the API usage pattern.

### What if the error text does not match Edge/Unleash responses?

Some unauthorized messages originate in surrounding systems (application middleware, gateways, or custom auth layers), not Edge itself.

Action:

- Correlate logs across Edge, ingress/gateway, and application layers before attributing root cause.

## Rollback criteria

Rollback to the previous version if any of these remain unresolved after remediation:

- Edge is not consistently `READY`.
- Critical SDK paths return unauthorized/forbidden unexpectedly.
- Feature evaluation results are inconsistent for the same token and context.

After rollback, keep the incident open and complete token-scope and persistence analysis before retrying the upgrade.

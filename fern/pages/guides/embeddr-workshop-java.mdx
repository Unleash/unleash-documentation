This workshop is built around Embeddr, a dating app for AI agents with a React frontend and a Java Spring Boot backend. The code lives in the [embeddr-workshop-java](https://github.com/Unleash/embeddr-workshop-java) repository on GitHub. You run your own copy of it and control it from your own Unleash project.

This workbook takes you through the whole workshop: setting up, wiring your first flag by hand, building a feature with an AI coding assistant, and then running an experiment, a safeguard, and a change request against your own copy of the app.

Work at your own pace. Each part ends with a checkpoint that tells you how to verify your progress before moving on. If you get stuck, raise a hand or ask your neighbor.

## The plan

Embeddr evaluates its feature flags on the backend through the [Unleash Java SDK](/sdks/java). The frontend holds no flag logic. The first half of the day is Unleash UI and a little Java. The AI assistant joins in part 4.

| Part | What you do | Where |
|------|-------------|-------|
| 0 | Register for your project, install a JDK and git, clone the repo, and run the pre-check | Terminal |
| 1 | Run Embeddr against your project: create `.env`, fill in two values, start the app | Unleash UI, terminal |
| 2 | Wire your first flag by hand: the waitlist from the opening demo, and let yourself in by user ID | Unleash UI, two lines of Java |
| 3 | Run an A/B test on the match layout with a success metric | Unleash UI, names in Java |
| 4 | Connect your assistant, have it build Embeddr Premium behind a flag, then kill the feature when its payment provider fails | Assistant, Unleash UI |
| 5 | Attach a safeguard to Auto-Rizz and trip it yourself | Unleash UI, names in Java |
| 6 | Ship light mode through a change request your neighbor approves | Unleash UI, names in Java, in pairs |
| 7 | Optional: retire the Premium flag through its lifecycle | Unleash UI, assistant |

## Part 1: run Embeddr against your project

Everything the app needs to reach Unleash lives in one file, `.env`. You create it first, keep it open, and fill in two values, each straight from the place you find it.

<Steps>
<Step title="Create .env">
In the terminal, inside the repo:

```bash
cp .env.example .env
```

Open `.env` in your editor and leave it open. It has three lines to fill. Two of them are for now. `UNLEASH_PAT` waits until part 4.
</Step>

<Step title="Sign in and paste the instance URL">
Check your email for the invitation to the workshop Unleash instance and sign in.

Open **Projects** in the sidebar, then look at the address bar. Copy everything before `/projects`, for example `https://us.app.unleash-hosted.com/abcd1234`, and paste it as the value of `UNLEASH_URL` in `.env`. No trailing slash.
</Step>

<Step title="Open your project">
Still under **Projects**, find the project named after you: first name, last initial, for example `Melinda F`. Open it.

The address bar now ends in `/projects/<your project id>`, for example `/projects/melinda-f`. That ID is yours for the day.

<Info>
Flag names are unique across the shared instance, so every flag you create is named `<flag>-<your project id>`, for example `early-access-melinda-f`.
</Info>
</Step>

<Step title="Create the backend token and paste it">
The app evaluates flags with its own [backend token](/concepts/api-tokens-and-client-keys#backend-tokens), scoped to your project.

1. In your project, go to **Settings**, then **API access**, then **New API token**.
2. Choose the **Backend** token type.
3. Scope it to the `development` environment, and create it.

<Frame background="subtle">
![The Create project API token dialog with the Backend SDK type and the development environment selected](/assets/embeddr-workshop-create-backend-token.png)
</Frame>

4. Copy the token. It looks like `melinda-f:development.xxxx`. Paste it as the value of `UNLEASH_BACKEND_TOKEN` in `.env`, and save the file.
</Step>

<Step title="Check and run">
```bash
./gradlew precheck
./gradlew bootRun
```

The `precheck` task verifies both values against the instance and tells you exactly which one is wrong if one is. It notes that `UNLEASH_PAT` is still empty. That is fine until part 4. The `bootRun` task builds the frontend and starts the app.

The app is up when the log says `Started EmbeddrApplication`. The task keeps running from then on: that is the server. It never reports done, and Ctrl-C stops it.

Open `http://localhost:8080`. You should see profile cards of AI agents looking for love. The terminal should also have logged `flags: synchronized with ...`.
</Step>
</Steps>

<Check>
**Checkpoint 1.** The app renders at `localhost:8080` and the log in your terminal shows `flags: synchronized`.
</Check>

<Accordion title="If something is off">

| Symptom | Likely cause |
|---------|--------------|
| `precheck` says it could not reach the instance | Network, VPN, or proxy. Run it again once you are online. |
| `precheck` says the backend token is rejected | Token scoped to the wrong project or environment, or `UNLEASH_URL` has a path after the instance, like `/api` or `/projects/...`. |

## Part 2: your first feature flag

At the start of the session the room queued at a waitlist and was let in a few people at a time. Now build that door yourself. No assistant yet: one flag in the UI, two lines of Java.

### Create the flag

<Steps>
<Step title="Start a new flag">
In your project, select **New feature flag**.
</Step>

<Step title="Name it">
Name it `early-access-<your project id>`, for example `early-access-melinda-f`.
</Step>

<Step title="Pick the type">
Flag type **Standard**, used for **Release**. Leave the expected lifetime at its default. It only sets a cleanup reminder.
</Step>

<Step title="Create it">
Select **Create flag**. The flag exists and is off in every environment.
</Step>
</Steps>

### Wire it up

The app keeps the name of every flag it uses in one file, `src/main/java/io/getunleash/embeddr/flags/Flags.java`. Open it and set `EARLY_ACCESS` to the exact name you just created:

```java title="Flags.java"
public static final String EARLY_ACCESS = "early-access-<your project id>";
```

For example `"early-access-melinda-f"`. The other names in that file stay as they are for now. You fill them in as you create those flags.

Now open `src/main/java/io/getunleash/embeddr/api/AccessController.java`. The door is wide open: the endpoint returns `true` for everyone. The controller already has the two things it needs, a `FeatureFlags` wrapper and a `Visitor` built from the session and the invite code. Replace the return line:

```java title="AccessController.java"
return new AccessResponse(flags.isEnabled(Flags.EARLY_ACCESS, visitor));
```

The wrapper hands the name and the visitor to the Unleash SDK, which evaluates the flag in memory from the copy of your project it fetched a few seconds ago. Read `flags/UnleashFeatureFlags.java` if you want to see exactly where that happens. It is the only class that imports Unleash.

Stop `bootRun` by pressing Ctrl-C in its terminal, run `./gradlew bootRun` again, and reload the browser. You should see the waitlist again, but this time it is controlled by the feature flag you created.

### Let yourself in

<Steps>
<Step title="Join the queue">
Type your first name as the invite code and press Enter. The page says you are in the queue and watches the door. The code you typed is now the Unleash `userId` on every request from this browser.
</Step>

<Step title="Add a strategy">
In the Unleash UI, open your flag. In the **development** environment, select **Add strategy**, then **Set up manually**.
</Step>

<Step title="Target your user ID">
In the **Targeting** tab, add a constraint: context field `userId`, operator `IN`, value your invite code, exactly as you typed it. Keep the rollout at 100 percent. Save the strategy.
</Step>

<Step title="Turn the environment on">
Turn the development environment on.
</Step>

<Step title="Watch the door open">
Within a few seconds the door opens and the cards appear.

Now open a private browser window, which is a new session, and type a different code. It waits at the door. That is one flag admitting one person, by user ID, with everybody else held outside.
</Step>
</Steps>

### Open the door wider

One [activation strategy](/concepts/activation-strategies) per flag is rarely the end of the story. Keep the one you have and add a second one next to it.

<Steps>
<Step title="Add a gradual rollout">
In the development environment, select **Add strategy** again, then **Gradual rollout**. Leave it without constraints and set the rollout to 50 percent. Save it.
</Step>

<Step title="Try a few sessions">
Open two or three fresh private windows and type a different code in each. Roughly half of them get in. Which half is decided by the code, because the invite code travels as the Unleash `userId` and the rollout [sticks](/concepts/stickiness) to it: the same code gets the same answer in every window, and a window keeps its answer every time it asks.
</Step>

<Step title="Open it fully">
Edit that strategy and move the rollout to 100 percent. Every window is in now, and so is everyone who comes later.
</Step>
</Steps>

Leave it at 100 percent. The rest of the workbook assumes the door is open for every session, including the private windows you open in part 3.

<Check>
**Checkpoint 2.** `early-access-<your project id>` exists and is on in development with two strategies: a `userId` constraint that let you in first, and a gradual rollout at 100 percent that lets everyone else in. Every window, private or not, shows the cards.
</Check>

<Accordion title="If something is off">

| Symptom | Likely cause |
|---------|--------------|
| The door never opens | The constraint value does not match what you typed, or the environment toggle is still off, or you forgot to restart `bootRun` after the code change. |
| Everyone gets in | The strategy has no constraint, or the line still returns `true`. |
| The door never opens, even without a constraint | `EARLY_ACCESS` in `Flags.java` is not exactly the name in Unleash. |
| Compile error on restart | The line needs `flags` and `visitor`, both already declared above it in the method, and `Flags` is already imported. |

</Accordion>

## Part 3: run an experiment

Embeddr wants to know how people prefer to browse matches: the classic grid, or one profile at a time. The code for both layouts is already in the app, and so is the success metric: every Match tap is counted under the layout that served it. All that is missing is the flag.

<Steps>
<Step title="Create the flag">
Create a flag named `match-layout-experiment-<your project id>`, flag type **Experiment**.
</Step>

<Step title="Set the names in Java">
In `Flags.java`, set `MATCH_LAYOUT_EXPERIMENT` to the flag you just created.

In `Metrics.java`, next to it, set the two match counters to `match_count_list_<your project id>` and `match_count_deck_<your project id>`, with underscores, for example `match_count_deck_melinda_f`.

<Warning>
Metric names follow Prometheus rules: letters, digits, and underscores only. Every hyphen in your project ID becomes an underscore here. The compiler will not catch a hyphen.
</Warning>

Metric names are unique across the instance too, and these keep your taps apart from the room's.

Restart `bootRun`.
</Step>

<Step title="Add a strategy with variants">
In the development environment, add a **Gradual rollout** strategy at 100 percent. In the strategy's **Variants** tab, add two [strategy variants](/concepts/strategy-variants), `list` and `deck`, with equal weights. Save, and turn the environment on.
</Step>

<Step title="Open a few sessions">
Reload the app, then open private windows, typing any invite code in each, until you have one window on each layout. The door is open for everyone since part 2. Each window is its own session and each session sticks to its side of the split, so it may take three or four windows before the deck shows up: one profile at a time, with Pass and Match.
</Step>

<Step title="Generate some data">
Tap **Match** a few times in each window.
</Step>

<Step title="Chart the metrics">
In the Unleash UI, open **Analytics** in the sidebar, then **Impact metrics**. Select **Add chart**, pick `match_count_list_<your project id>` from the metric list, keep aggregation **Count**, and save. Add a second chart the same way for `match_count_deck_<your project id>`.
</Step>

<Step title="Wait for the charts">
The app sends its counts every five seconds, but the charts aggregate on the Unleash side and the first points can take a minute or two to show up. Tap Match a few more times while you wait, and refresh the page if nothing has moved after two minutes.

Then the two charts climb independently: your taps in the grid window on one, your taps in the deck window on the other.
</Step>
</Steps>

<Tip>
The variant name travels from Unleash, through `flags.variant(...)` in `LayoutController`, to the frontend, which picks the component. The tap travels back through `MatchController`, which asks for the same variant and counts under it. Nothing in the frontend knows there is an experiment. Read more about [impact metrics](/concepts/impact-metrics).
</Tip>

<Check>
**Checkpoint 3.** Your normal browser window and at least one private window show different layouts, one the card grid and one the deck, and the two match counters move independently in Unleash.
</Check>

### Build Embeddr Premium

Embeddr wants to monetize. The free tier shows six matches. Embeddr Premium promises the rest of the embedding space, for a price. Product is excited. Finance is more excited. Let's see.

<Steps>
<Step title="Give your assistant the prompt">
```text title="Prompt"
Add an embeddr premium upsell that shows a premium call to action in the
match grid inviting the user to subscribe to see more models. Hook it up
to our payment provider.
```
</Step>

<Step title="Watch what it does">
Notice the prompt never says the words feature flag. Deciding that this change needs one is the assistant's job. Expect it to:

- Evaluate the change through the MCP server and decide it needs a release flag for Premium.
- Create it in your project, with your project ID in the name, like `premium-upsell-melinda-f`, and add it to `Flags.java`.
- Write a controller that serves the call to action only when the flag is on, an upgrade endpoint that charges through the payment provider, and the frontend that renders it all.
</Step>

<Step title="Verify in the Unleash UI">
Your project shows one new flag, off in every environment.
</Step>

<Step title="Restart and look">
Restart `bootRun`: Ctrl-C in its terminal, then `./gradlew bootRun`. The restart rebuilds the frontend too.

Look at the app. No call to action anywhere yet. The code is there. The feature is not released.
</Step>
</Steps>

<Check>
**Checkpoint 5.** The Premium flag exists in your project, turned off, and the app shows no premium call to action.
</Check>

### Release it, break it, kill it

<Steps>
<Step title="Release it">
Turn the Premium flag on in development with a gradual rollout at 100 percent, in the UI or by prompt:

```text title="Prompt"
Turn on the premium flag in the development environment with a gradual
rollout at 100 percent.
```
</Step>

<Step title="Break it">
Within a few seconds the call to action appears. Tap **Upgrade**. The payment provider thinks for a second and fails. It always fails. It is built that way. In real life this is the Monday morning incident.
</Step>

<Step title="Kill it">
You have one runtime move and no deploy: turn the Premium flag off. The call to action vanishes within a few seconds while the app keeps running, and nobody else hits the broken provider.
</Step>
</Steps>

<Info>
**Kill switch versus release flag.** What you just flipped is a release flag. It is meant to be temporary: it ships Premium, and once Premium is stable the flag gets cleaned up in part 7. You can still operate it as a kill switch, because turning it off removes the functionality in seconds, and in an incident that is what counts.

A proper kill switch is different in two ways: it is long lived, and it is inverted, so off means "normal" and on means "bypass". If Embeddr's payment provider were known to misbehave long term, you would wrap the call to it in a `kill-switch` flag of its own, keep that flag for as long as the provider is around, and flip it on whenever the provider acts up, without touching the Premium release flag at all.
</Info>

<Check>
**Checkpoint 6.** You watched Upgrade fail, turned Premium off, and watched the call to action disappear, without restarting anything.
</Check>

<Accordion title="If something is off">

| Symptom | Likely cause |
|---------|--------------|
| The assistant cannot decide where to create the flag | Not a failure. Tell it your project ID. |
| The assistant created the flag without your project ID in the name | Ask it to archive that one and create `premium-upsell-<your project id>`. Or create the flag yourself with FALLBACKS.md and ask only for the code. |
| The flag is on but nothing shows | The flag name in the Java code and in Unleash do not match, or `bootRun` was not restarted after the code change. |
| The assistant started a server or ran a build that failed | Stop it, restart `bootRun` yourself, and ask it to fix the specific compile error you see. |

</Accordion>

<Tip>
**If your assistant misbehaves:** create the flag yourself with the create-flag command in [FALLBACKS.md](https://github.com/Unleash/embeddr-workshop-java/blob/main/FALLBACKS.md#create-a-flag), then ask the assistant to write only the code. If the code is wrong, ask it to fix the specific problem you see. You do not need to start over.
</Tip>

## Part 5: let a safeguard protect the flag

Auto-Rizz writes an opening line on every match card. Users can tap **Ick**, the thumbs down, and every tap increments the thumbs down impact metric. In this part you roll the feature out, then attach a [safeguard](/concepts/impact-metrics#configure-safeguards) that turns it off when the thumbs down count goes above a threshold you set.

<Steps>
<Step title="Create the flag">
Create a flag named `auto-rizz-<your project id>`, flag type **Standard**, used for **Release**.
</Step>

<Step title="Set the names in Java">
In `Flags.java`, set `AUTO_RIZZ` to that name. In `Metrics.java`, set `THUMBS_DOWN_COUNT` to `thumbs_down_count_<your project id>`, with underscores. Restart `bootRun`.
</Step>

<Step title="Apply a release template">
This time, no hand-made strategy. In the flag's development environment, select **Use template** and pick **Progressive percentage-based rollout**. It adds a [release plan](/concepts/release-templates) with four milestones: 25, 50, 75, and 100 percent.

Turn the environment on. The first milestone starts and a quarter of sessions get openers, which may or may not include yours.
</Step>

<Step title="Walk the plan forward">
On the release plan, start the next milestone, then the next, until the 100 percent milestone is active. Reload the app: every card has an opener, and an Ick button.

In real life each milestone would run for days while you watch the metrics. Today the safeguard does the watching, so you can skip ahead.
</Step>

<Step title="Create the metric">
Tap Ick once, so the metric exists. The app reports metrics every five seconds.
</Step>

<Step title="Add the safeguard">
In the flag's development environment, add a **Safeguard**. Pick your thumbs down metric, aggregation **Count**, a threshold of 3, over the shortest window offered. The action is to disable the environment. The presenter walks through the dialog on screen.
</Step>

<Step title="Trip it">
Tap Ick four more times. Watch the flag. Within a minute or two the safeguard trips, the environment turns off, and the openers vanish from your app. Nobody at the keyboard.
</Step>
</Steps>

This is the demo from the start of the session, running in your project against your app. What you did by hand in part 4 is what the safeguard does on its own.

<Check>
**Checkpoint 7.** The development environment of your Auto-Rizz flag shows it was disabled by the safeguard, and the openers are gone from the app.
</Check>

<Accordion title="If something is off">

| Symptom | Likely cause |
|---------|--------------|
| No openers after walking the plan to 100 percent | `AUTO_RIZZ` in `Flags.java` is not exactly the name in Unleash, or `bootRun` was not restarted, or the environment toggle is off. |
| The safeguard never trips | The metric it watches is not the one in `Metrics.java`. Check the spelling and underscores. Or the taps were spread over more than one window: tap three more times within a minute and wait again. |
| The safeguard tripped before you were ready | The first tap, the one that created the metric, counted too. That is fine. Turn the environment back on and tap again. |

</Accordion>

## Part 6: ship through a change request

In production, nobody flips flags alone. In this part you turn that rule on for your own project, and since you cannot approve your own request, you need a reviewer. Pair up with a neighbor.

### Require a review

<Steps>
<Step title="Open the configuration">
In your project, go to **Settings**, then **Change request configuration**.
</Step>

<Step title="Turn change requests on">
Turn [change requests](/concepts/change-requests) on for the **development** environment and set the required approvals to 1. Leave production as it is.
</Step>
</Steps>

From now on, every change to a flag in development lands in a draft that someone else has to approve.

### Let your reviewer in

<Steps>
<Step title="Open user access">
Still in **Settings**, open **User access** and select **Assign user/group**.
</Step>

<Step title="Assign the Reviewer role">
Search for your neighbor by email, give them the **Reviewer** role, and save. Reviewer is a [custom project role](/concepts/rbac#custom-project-roles) set up for this workshop: it can approve and apply change requests in your project and nothing else. Your neighbor does the same for you in their project.
</Step>

<Step title="Reload">
Your neighbor's project now shows up in your project list, and yours in theirs.
</Step>
</Steps>

### Ship light mode

<Steps>
<Step title="Create the flag">
Create a flag named `light-mode-<your project id>`, flag type **Standard**, used for **Release**. It gates the theme toggle in the header. The code is already wired.
</Step>

<Step title="Set the name in Java">
In `Flags.java`, set `LIGHT_MODE` to that name. Restart `bootRun`.
</Step>

<Step title="Make the change">
In development, add a gradual rollout at 100 percent and turn the environment on. Nothing happens yet: both changes landed in a draft change request instead of in the environment.
</Step>

<Step title="Submit for review">
Open the draft, add a short description, and submit it for review.
</Step>

<Step title="Have it approved">
Your neighbor opens your project, finds the change request under **Change requests**, reviews it, approves it, and applies it.
</Step>

<Step title="Watch your app">
The theme toggle appears in the header. Then do the same for your neighbor.
</Step>
</Steps>

<Check>
**Checkpoint 8.** Change requests are on in your development environment, your neighbor is a Reviewer in your project, your light mode change request shows approved and applied by them, and the toggle is in your header.
</Check>

<Accordion title="If something is off">

| Symptom | Likely cause |
|---------|--------------|
| There is no **Assign user/group** button | You are a Member of your own project rather than its Owner. Ask an organizer to fix the role. |
| You cannot find your neighbor in the user search | They registered with a different email than the one they gave you, or they have not accepted the instance invitation yet. |
| Your neighbor sees the project but no Approve button | They got the Member role instead of Reviewer. Change it under **User access**. |
| The flag turned on immediately, no draft | Change requests are not on for your development environment. Check **Settings**, then **Change request configuration**. |

</Accordion>

## Part 7: retire a flag

<Note>
This part is optional. If the room runs late, skip it.
</Note>

A release flag like Premium is supposed to be temporary: once the feature is fully rolled out and stable, the flag becomes debt. Unleash tracks this as a [lifecycle](/concepts/feature-flags#feature-flag-lifecycle): **Define**, **Develop**, **Production**, **Cleanup**, **Archived**.

<Frame background="subtle">
![A project's flag lifecycle view, counting flags in the Define, Develop, Production, Cleanup, and Archived stages](/assets/embeddr-workshop-flag-lifecycle-stages.png)
</Frame>

<Steps>
<Step title="Mark it ready for cleanup">
Open your Premium flag and find its lifecycle stage. Hover over it and select **Mark ready for cleanup**.
</Step>

<Step title="Remove the flag from the code">
Ask your assistant:

```text title="Prompt"
Embeddr Premium is now fully rolled out. Remove the flag from the code.
```
</Step>

<Step title="Verify without the flag">
Restart `bootRun` and verify the call to action still renders, now without a flag behind it.
</Step>

<Step title="Archive the flag">
Archive the flag in the Unleash UI. Change requests are still on from part 6, so the archive lands in a draft: submit it and have your neighbor approve it. Retiring a flag goes through review like any other change.
</Step>
</Steps>

<Check>
**Checkpoint 9.** The Premium flag went develop, cleanup, archived, and the feature still works as a permanent part of the app.
</Check>
